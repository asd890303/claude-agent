# 註解與 JSDoc 撰寫規範

核心判準：**拿掉這句註解，讀者會誤解或漏掉什麼重要資訊？不會就不寫。**
面向永遠是「從未見過歷史、第一次讀這段程式碼的人」，不是「這次改了什麼」。

## 一、不主動新增

- 預設**不主動新增**解釋性註解／JSDoc，除非使用者明確要求
- 型別與命名已表達的資訊，不用文字再重複一次
- 顯而易見、自解釋的函式：省略 JSDoc，或只留一行
- 需要寫時（共用 utils、非顯而易見的邊界行為／陷阱），只描述「**現在做什麼、為什麼這樣做**」

## 二、禁止變更歷史語句

註解只描述「現在的狀態」，**不得描述 diff**。禁止出現：

- 中文：之前／原本／上一版／舊的／現在改成／更新為／新增了／移除了／修改了
- 英文：`Previously` / `Used to` / `Changed from X to Y` / `Refactored to`

變更原因與新舊對比寫進 **commit message／PR 描述**，不寫進程式碼註解。

## 三、JSDoc 補「為什麼」與「不明顯的行為」

優先補下列型別系統表達不了的資訊，不要把型別再用文字翻譯一次：

- 副作用
- `null` / `undefined` 代表的意義
- 是否修改輸入參數
- 非同步時序
- 快取行為
- 各種陷阱／邊界條件

複雜或多情境的函式可用 `@example` 示範用法；棄用改用 `@deprecated` + `@see` 指向替代方案，**不寫棄用的歷史細節**。

## 四、不主動刪除既有註解

- **不得主動刪除**任何既有註解（`//`、`/* */`、`<!-- -->`）
- **不得主動刪除**開發用語法（`console.log/warn/error`、`print`、`logger`、`debugger` 等）
- **不得主動刪除** commented-out 程式碼區塊（即使看起來沒用）
- 有疑慮時先詢問，由使用者決定；只有明確指示「移除／刪掉／清掉」時才刪

> 本規範「不主動新增」與「不主動刪除」是兩件事：前者管新寫的內容，後者保護既有內容，不代表要回頭清理舊註解。
